# kairos-whiteboard-video

**Knowledge → Whiteboard Video Compiler**

将文章、机制、现象、观点或其他知识内容，编译为「边讲边画、逐步揭示、音画同步」的白板讲解视频。

本项目不是一个单纯的动画渲染器，而是一条从**知识理解 → 认知结构 → 表达设计 → 视觉揭示 → 时间编排 → 视频渲染**的确定性生产管线。

> **Current status:** Production pilot stage  
> **Engine:** Python 3.11+ / OpenCV / FFmpeg  
> **Board images:** Generated by the host image-generation model  
> **License:** MIT

---

## 1. What it does

给定一份知识内容，系统依次完成：

```
Knowledge
   ↓
Knowledge Model
   ↓
Learner Model / Cognitive Transitions
   ↓
Expression Plan
   ↓
Scene + Beat Timeline
   ↓
Board Image + Reveal Operations
   ↓
Voice / Word Timing
   ↓
Whiteboard Rendering
   ↓
Final Video
```

核心思想：

- **认知结构先于视觉设计**：先确定观众需要完成哪些认知转变，再决定画什么。
- **Beat 是认知单位，Scene 是画布容器**：Scene 数量不等于 Beat 数量。
- **视觉状态随认知状态增长**：画面不是一次性出现，而是在讲解过程中逐步揭示。
- **真实语音决定时间**：成片时间以 TTS 产生的词级时间戳为准，而不是按字数估算。
- **内容与视觉分离**：板图负责内容，layout / annotation / subtitle 属于渲染层。
- **主题是稳定的视觉约束**：颜色、线条、角色、手笔素材和生成规则由主题包统一管理。
- **质量门控制流程**：内容、视觉、最终产物分别确认，避免未经确认的结果直接进入下游。

## 2. Core capabilities

### 2.1 Knowledge → Cognitive Structure

每一期内容首先建立语义 IR：

- `knowledge_model`
  - `target_claim`
  - `task_type`
  - `model`
  - `evidence`
  - `scope`
- `learner_model`
  - `constraints`
  - `transitions[]`
- `scenes[].beats[]`

系统使用 Transition、Merge Test、Split Test 等规则确定 Beat 结构，避免按照“固定五段式”或内容长度机械切分。

### 2.2 Word-level Audio Synchronization

TTS 生成：

- `narration.mp3`
- `words.json`

后续时间轴从真实语音边界派生：

- 场景时长
- 句级 narration span
- 绘制开始与结束时间
- 字幕高亮时间

因此，**字数只用于前期估算，成片时间不由字数决定。**

### 2.3 Progressive Whiteboard Reveal

当前渲染模型以“增量揭示”为核心：

- `DRAW`
- `CONNECT`
- `GROUP`
- `ANNOTATE`
- 追加式 `CHANGE`

渲染器维护持续存在的白板状态，通过分区时序、骨架描线和蛇形填色逐步形成最终画面。

### 2.4 Character Consistency

涉及人物的项目使用：

```
Character ID
   ↓
Character Bible
   ↓
Immutable Anchors
   ↓
Canonical Character Sheet
   ↓
Reference Images
   ↓
Scene Reference Manifest
   ↓
Scene Prompts
```

角色身份在项目内通过 `input/characters.json` 固定。

其中：

- `immutable`：发型、脸型、眼睛、眼镜、服装、主色、比例等不可随场景改变的身份锚点。
- `allowed_variations`：姿势、表情、视角、剧情道具等允许变化的属性。
- `reference_images`：跨场景一致性的真实参考图。
- `character-sheet.prompt.txt`：用于生成 canonical character sheet。
- `character-reference-manifest.json`：记录每个场景实际使用的角色参考图。

> 文字 Character Bible 只能约束生成意图，不能替代图像参考。最终一致性仍取决于宿主图像模型对 reference image 的支持能力。

### 2.5 Theme System

主题包统一管理：

- 视觉风格
- 调色板
- 角色契约
- 手笔素材
- 笔尖锚点
- 渲染模式
- 主题级参考图约束

当前冻结主题：

| ID | Name | Renderer | Resolution |
| --- | --- | --- | --- |
| `chalkboard-chibi` | 黑板粉笔 Q 版讲解 | chalk | 1920×1080 |

默认主题以项目的参考板图为视觉合同：深墨绿黑板、暖象牙细线、低饱和辅助色、紧凑的信息岛布局，以及独立的前景粉笔手素材。

**板图本身不得生成手。** 手由渲染器使用主题包中的 canonical asset 叠加，以避免每幕手型、位置和画风漂移。

## 3. Production workflow

一期视频采用三个质量门：

```
┌──────────────────────────┐
│ 1. Content & Direction   │
│ knowledge → script → IR  │
└────────────┬─────────────┘
             │ confirm-content
             ↓
┌──────────────────────────┐
│ 2. Visual Design         │
│ prompts → boards → layout│
│ → annotate → review      │
└────────────┬─────────────┘
             │ confirm-visual
             ↓
┌──────────────────────────┐
│ 3. Final Delivery        │
│ voice → render → assemble │
│ → validate → final review │
└────────────┬─────────────┘
             │ confirm-final
             ↓
          Delivery
```

### Stage 1 — Content & Direction

输入可以是一句话，也可以是一篇完整文章。

主要产出：

- 表达设计卡
- `input/script.json`
- 推荐主题
- 知识模型
- Learner Model
- Scene / Beat 结构

进入下一阶段前必须：

- IR 合法
- `lint` 无 blocking findings
- 用户确认内容、方向和主题

### Stage 2 — Visual Design

主要步骤：

1. 根据主题生成全部场景 prompt。
2. 使用宿主图像模型批量生成场景板图。
3. 导入并标准化为 1920×1080。
4. 清理生成平台水印。
5. 自动生成 layout。
6. 根据词级时间轴生成 annotation。
7. 人工检查板图和绘制顺序。

板图生成由**宿主模型**完成；本项目不绑定某个具体图像模型，也不在引擎内部运行扩散模型。

进入下一阶段前必须：

- 所有场景板图通过自动检查
- layout / annotation 完整
- 不存在降级 warning
- 用户确认视觉方案

### Stage 3 — Final Delivery

主要步骤：

1. TTS
2. 词级时间戳生成
3. 场景并行渲染
4. 视频合成
5. 字幕生成
6. 全量验证
7. 最终人工确认

最终交付：

```
projects/<episode-id>/deliverables/final.mp4
```

## 4. Quick start

### Requirements

- Python **3.11+**
- [uv](https://docs.astral.sh/uv/)
- FFmpeg
- Network access for Edge TTS and host-side image generation

### Install

```bash
cd engine
uv sync
```

### Initialize an episode

```bash
uv run python scripts/workflow.py init \
  --episode-dir ../projects/my-episode \
  --title "我的第一期白板视频"
```

可选：

```bash
--scenes 7
```

但实际 Scene 数量以最终 `script.json` 为准。

### Check project status

```bash
uv run python scripts/workflow.py status \
  --episode-dir ../projects/my-episode
```

### Validate the content IR

```bash
uv run python scripts/workflow.py lint \
  --episode-dir ../projects/my-episode
```

### Generate board prompts

```bash
uv run python scripts/workflow.py prompts \
  --episode-dir ../projects/my-episode \
  --theme ../themes/chalkboard-chibi
```

`prompts` **只生成 prompt，不负责调用图像模型。**

使用宿主模型按生成结果写入：

```
projects/my-episode/build/boards/
├── scene-01.png
├── scene-02.png
└── ...
```

### Import boards

```bash
uv run python scripts/workflow.py import \
  --episode-dir ../projects/my-episode \
  --boards-dir ../projects/my-episode/build/boards \
  --theme ../themes/chalkboard-chibi
```

### Generate voice

```bash
uv run python scripts/workflow.py voice \
  --episode-dir ../projects/my-episode
```

### Layout and annotation

```bash
uv run python scripts/build_video.py \
  --episode-dir ../projects/my-episode layout

uv run python scripts/build_video.py \
  --episode-dir ../projects/my-episode annotate
```

### Confirm visual design

```bash
uv run python scripts/workflow.py confirm-visual \
  --episode-dir ../projects/my-episode
```

### Render

```bash
uv run python scripts/build_video.py \
  --episode-dir ../projects/my-episode render --jobs 4
```

也可以只渲染一幕：

```bash
uv run python scripts/build_video.py \
  --episode-dir ../projects/my-episode render \
  --scene scene-03
```

### Assemble

```bash
uv run python scripts/build_video.py \
  --episode-dir ../projects/my-episode assemble
```

### Validate final output

```bash
uv run python scripts/workflow.py validate \
  --episode-dir ../projects/my-episode --full
```

### Confirm final delivery

```bash
uv run python scripts/workflow.py confirm-final \
  --episode-dir ../projects/my-episode
```

## 5. Command reference

### Workflow commands

| Command | Purpose |
| --- | --- |
| `init` | 初始化一期项目 |
| `status` | 查看当前阶段和质量门状态 |
| `sync-boards` | 根据 `script.json` 同步 Scene 列表 |
| `voice` | 生成 TTS 与词级时间戳 |
| `confirm-voice` | 兼容旧流程的语音状态命令 |
| `prompts` | 生成宿主模型使用的板图 prompt |
| `probe` | 运行主题探针 |
| `lint` | 校验知识 / 学习者 / Beat / 表达 IR |
| `spans` | 从词级时间戳派生句级 narration spans |
| `import` | 导入、检查、标准化板图 |
| `confirm-content` | 第 1 次质量门 |
| `confirm-visual` | 第 2 次质量门 |
| `confirm-final` | 第 3 次质量门 |
| `confirm-boards` | 旧流程兼容命令 |
| `render` | 渲染场景 |
| `validate` | 执行交付前验证 |

`build_video.py` 负责确定性的视觉构建：

| Command | Purpose |
| --- | --- |
| `layout` | 生成版式和原始板面 |
| `annotate` | 根据脚本与时间轴生成绘制标注 |
| `render` | 渲染逐步绘制动画 |
| `assemble` | 合成场景、旁白和字幕 |


单期生成物原则上不进入仓库；修改引擎后应通过现有输入重新生成。

## 7. Quality gates

项目把质量控制分成三层。

### Content gate

检查：

- Knowledge Model 完整
- Learner Model 合法
- Transition 与 Beat 对齐
- Expression Plan 合法
- Scene 分组合理
- `lint` 无 blocking findings

### Visual gate

检查：

- 板图尺寸和比例
- 主题一致性
- 角色一致性
- 背景稳定性
- layout 与 elements 一一对应
- 词级 anchor 匹配
- annotation 无降级
- 手素材与主题匹配

### Final gate

检查：

- 所有场景成功渲染
- 场景时长与语音一致
- 音画同步
- 字幕可用
- 视频规格正确
- 死寂、扫荡、切幕、残影、幕末缺墨等 QA gate 无阻断
- `final.mp4` 存在并可播放

只有三个质量门全部通过，项目才进入交付状态。

## 8. Design constraints

以下约束属于系统设计的一部分，而不是建议：

### Board image

- 板图不生成可读文字。
- 编号、标签和字幕由渲染 / overlay 层负责。
- 不允许通过非等比缩放修正板图比例。
- 当前标准输出为 1920×1080。

### Timing

- 真实词级语音边界是时间轴的权威来源。
- 找不到词级 anchor 时只能暂时降级，正式交付前必须修复。
- 场景末尾必须保留必要的视觉停留时间，不能让绘制在语音结束前被截断。

### Rendering

- 渲染是增量揭示，不是每幕重新绘制整张白板。
- 当前核心内核采用持续画布 + delta reveal。
- `HIGHLIGHT`、元素级 `REMOVE`、`REFRAME` 等尚未实现的操作不得进入正式表达计划。

### Theme

主题必须经过探针验证后才能登记到 `themes/registry.json`。

主题包应同时定义：

- visual style
- palette
- character contract
- hand asset
- hand tip anchor
- renderer mode

## 9. Development

### Run tests

```bash
cd engine
uv sync
uv run pytest -q
```

### Recommended validation loop

开发引擎时不要默认全量重跑：

```
修改引擎
  ↓
单幕 render
  ↓
检查单幕结果
  ↓
修复
  ↓
全量 render
  ↓
assemble
  ↓
validate --full
```

只有在单幕验证通过后才进入全量渲染。

### External image generation

本项目只负责：

1. 生成结构化 prompt
2. 接收宿主模型生成的板图
3. 校验和标准化板图
4. 将板图纳入确定性的渲染流程

项目**不内置或绑定特定文生图模型**。

因此，图像生成质量属于宿主模型能力与主题约束共同决定的变量；引擎侧通过 prompt contract、reference image、asset contract 和自动检查降低不确定性。

## 11. Known limitations

当前系统仍有明确边界：

- 板图生成依赖宿主图像模型，不保证所有模型都能稳定遵守复杂视觉约束。
- Character reference 能显著提高一致性，但不能从工程层面保证生成模型实现像素级身份一致。
- 当前 `themes/registry.json` 只有一个经过冻结验证的主题。
- 白板渲染内核仍以追加式揭示为主，不支持任意擦除和自由镜头运动。
- 发布动作不由 agent 自动执行。

这些限制应在生产评估中单独记录，而不是通过流程文档掩盖。
