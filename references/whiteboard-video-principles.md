# 白板知识科普视频第一性原理（whiteboard-video-principles）

> 回答一个问题：**什么叫白板知识科普视频**。下游三份文档（cognitive-timeline / script-design / engine-design）
> 的全部规则都必须能回溯到本文的某条原理；回溯不到的规则视为冗余，应删。

## 1. 定义

一句话：**白板知识科普视频 = 用增量揭示的方式，在观众脑子里逐步建立一个解释模型。**

它不是三种东西：

- 不是"配了画的朗读"——画面若不承担认知增量，就是装饰；
- 不是"会动的 PPT"——PPT 一次性给出整页结论，白板给出的是结论**形成过程**；
- 不是"手绘风格的动画短片"——手绘只是当前主题包的视觉身份，不是这门工艺的本质。

反面判据：把画面静音只看图，观众能否说出模型的骨架？把声音关掉只看逐步出现的图，
能否比听音频更早理解到位？两问都答"否"，说明画面没有承担认知，只是配音的贴图。

## 2. 六条第一性原理

### P1 白板的核心不是手绘，是"空间结构持续保留 + 视觉状态可增长"

严谨表述：**白板是一种允许持续保留空间结构、同时通过渐进式绘制改变视觉状态的呈现机制。**
它的工程优势在于视觉状态能跟着认知状态一起长：

```
Previous State → Add → Modify → Connect → Final State
```

白板适合表达的是**渐进式建立解释模型**：

```
A          →  A B       →  A B C      →  A→B→C（关系成立）
```

观众看到的不是三张图，是同一个模型在长。所以本项目最重要的资产不是画风，
是"每一步在长哪一块"的切法（切法定义见 `cognitive-timeline.md` §6.1 逆向切图 与 §9 Reveal Constraint）。

结论边界（不自大）：多媒体学习研究支持分段、预先提示、时空邻接以及**渐进绘制与叙事结合**
能改善部分学习结果（Cambridge Handbook of Multimedia Learning 的 segmenting / pretraining /
modality 原则；Heliyon 2023 的白板动画实验）。这不等于"白板天然优于其他教学媒介"——
效果与情境、设计相关。所以本项目只在**知识本身有可增长的结构**时选它（§4 适用边界），
不宣称它是普适最优解。

推论：手绘感、笔迹、抬笔、手部素材，都是为了让"长出来"这件事可信的**服务层**，
本身不构成价值。画风再像真人，若画面一次性给完，仍然是 PPT。

### P2 一切时间从真实语音边界推导

讲解是主轴，画面是 follower。时间基准只能是配音的实际词级边界（`words.json`），
不能是字数估算。区段均分在引擎里是**降级兜底**（找不到词级锚时才出现），
一旦出现即视为脚本 anchor 有缺陷：必须改 anchor 重跑，不得带着降级进二审。
估算只用于立项阶段判断"这期大概多长、该拆几步"，一旦真实配音生成，所有派生时间以实测为准重算。

### P3 视觉信息不得无理由领先于讲解所需的认知信息

这是本项目对"AI 味"给出的**唯一定义**，也是通用规则，与画风无关。

AI 味真正的来源是结构，不是画质：

```
AI 常做的结构：  完整答案 → 完整画面 → 完整画面 → 完整答案
好的白板结构：  问题 → 局部信息 → 建立关系 → 修正 → 新信息 → 结论
```

前者每一帧都已经知道结局，所以"一眼 AI"；后者每一刻观众和画面一起不确定，
所以像人在讲。因此"降低 AI 痕迹"不写进视觉风格规则，只写进时序规则。

形式化表述（完整定义与四种合法隐藏见 `cognitive-timeline.md` §9）：

```
Beat n 期间：Visible ⊆ Required(n) + Deliberate Context
```

两个方向的违规（合格线都是 0）：

- **领先违规**：把观众尚未被引导理解的关键关系提前画全——视觉替观众完成了推理；
- **落后违规**：旁白已进入新 Beat，画面仍在补上一 Beat 的元素超过一句
  （观众听到"这个"而画面上还没有"这个"）。

允许的唯一例外：**钩子式预告**——故意留一个
未解释的元素制造悬念，必须在卡里显式登记 `hook=true`，否则按违规处理。

### P4 先看得懂，再讲得好

科普片的底线是专业与严谨，通俗是第二性；但**观众看不懂的表达，是作者的失败**，不是观众的失败。

- **比喻必须自带操作解释**：旁白用了比喻，同一 Beat 内必须说清"具体要做什么"。只说
  "从外面掷个骰子"不合格；"让 AI 先跑一段代码，生成一长串随机的字母数字"才合格。
- **禁止本片自造黑话**：不得临时发明只在本片成立的词（"破法""演随机""从外面喂"这类）。
  要么用大白话里本来就有的类比（"词语接龙"），要么当场解释清楚。
- **忠于来源**：数字、模型名、做法与来源材料一致，不夸大、不脑补；来源没有的内容一律不进片。

验收判据一句话：观众听完每个 Beat，能否复述出"我具体要敲什么"。
（2026-09-03 一期口播返工教训——比喻先行、操作缺位，整段听不懂。）

### P5 结构由认知转变的数量决定，不由长度决定

> **Beat 数量 = 不可合并的认知转变数量。** 不是内容长度、不是目标秒数、不是"科普片就五段"。

推论三条：

- 一条知识该出几个 Beat，是 `learner-model.md` **求解**出来的（约束 → 候选转变 → Merge Test），
  所以 **Timeline 是规划结果，不是原始数据**；任何"先定五幕再往里填"的做法都绕过编译器。
- **单期时长不设上限**（目标是优质，不是短）。所以时长**不增减 Beat**，只用于节奏与单步负荷的
  判断；拆成多期的唯一合法理由是认知完整性——一条链只能承载一个 `target_claim`，
  出现第二个独立主张才拆（`knowledge-model.md` §7）。"怕太长"不是砍 Beat 的理由。
- 反过来讲：如果两次规划给出的 Beat 数不一样，说明约束或障碍识别有漏，
  不是"这次想短一点"——数量差异必须能被解释。

这条是本项目防"随手切幕"的主闸，也是 Skill 区别于 prompt 模板的地方。

### P6 两条通道服务同一个认知任务：互补，不重复；元素必须有认知职责

语言与视觉不是两个独立生成器。推论三条：

- **通道分工**：因果与理由归语言，空间结构与量的对比归画面，命名与关键动作时刻必须同步
  （`expression-plan.md` §6 的 VERBAL / VISUAL / SHARED 分配）。
- **不机械重复**：画面已经表达清楚的关系，旁白逐条再念一遍就是浪费观众的听觉带宽。
  但也**不能把"绝不写字"当规律**——冗余原则是有条件的，短而贴住关键动作的屏幕标注反而降负荷
  （本项目即版式层叠加的 ≤7 字标签）。
- **元素要有认知职责**：每个画面对象必须答得出"它代表什么、承担哪次认知职责、哪个 Beat 引入、
  之后谁还在用"。答不出"为什么它现在存在"就删——它只会增加无关处理。

研究边界（同 P1）：连贯性、信号提示、空间/时间邻接等原则能降低无关处理、改善部分学习结果，
不是普适保证；所以 P6 落成**可检查的编译约束**，不写成"这样一定更好"的断言。

## 3. 职责分离：模型管终态，引擎管过程

```
宿主文生图模型  →  负责"这一幕最后长什么样"（整幕板图，静态、无文字）
渲染引擎        →  负责"怎么一步步画出来"（分区、笔画、时序、手部、合成）
```

这条分工不是偷懒的妥协，是 P1 的必然结果：模型擅长一次成图，不擅长控制揭示时序；
引擎擅长确定性时序，不擅长凭空创造构图。所以 Beat 序列只写"新增哪一块"，
终态由模型一次画全，过程由引擎反推。谁越界谁劣化——让模型出分镜动画会得到
时序不可控的抖动的视频，让引擎构图会得到没有灵魂的几何堆。

## 4. 适用与不适用

适合做成白板科普：有**结构**或**演进过程**的知识——机制、流程、对比、因果链、
概念辨析、方法步骤、系统关系。

不适合（应换形态：口播真人出镜、图文卡片、演示录屏）：

- 纯资讯与时效播报（没有模型可建立）；
- 纯情绪与观点宣泄（解释模型不是目的）；
- 平铺清单（十条 Tips 之间无关系，画成图只是编号框）；
- 强依赖真实影像的实操演示（软件点击、硬件动作）。

选题阶段先过这一关，避免用白板工艺硬做不适合的知识。

## 5. 术语表

| 术语 | 定义 |
|---|---|
| 认知差 | 观众看前的理解状态与看后的理解状态之间的差，本片唯一目标 |
| Beat | 最小的、能明确描述"观众认知状态变了什么"的单元，**必须有 before / after**（`cognitive-timeline.md` §4） |
| Scene / 幕 | 制作单位：一段口播 + 一张板图 + 一段绘制过程；**板面容器，与 Beat 数无固定比例** |
| Beat Grouping | 把 Beat 分组落到 Scene 上的决策（共享板面结构 / 清屏重装 / 揭示连续性） |
| Knowledge Model | 编译器前端**语义 IR**：`target_claim / task_type / learner / model.core+nodes+relations / learning_outcome / evidence / dependencies / scope` |
| Knowledge Graph | `model.nodes + model.relations` 的偏序结构，不分先后；线性化后才成 Timeline |
| Learner Model | 知识到认知路径之间的**转换器**：约束求解 + 转变规划；Learner Constraints 是其第一阶段 |
| Transition | Learner Model 的基本单位：`from_state →(operation, obstacle)→ to_state`，不是 Step |
| cognitive_operation | 五种认知目标：IDENTIFY / DISTINGUISH / RELATE / EXPLAIN / APPLY |
| obstacle | 六种认知障碍：MISSING / CONFLICT / GAP / ABSTRACTION / OVERLOAD / TRANSFER |
| Merge Test | 判断两个候选转变能否合并的四条件；**Beat 数 = 合并后剩余转变数** |
| task_type | 教学任务类型：A 纠正误解 / B 建立新概念 / C 解释机制 / D 建立概念间关系（可混合），决定 misconception 是否必填 |
| evidence 三档 | `source-backed fact` / `model inference` / `teaching simplification`；未登记的简化就是幻觉（P4） |
| Learner State (Si) | 观众在第 i 步**持有的解释模型**；Timeline 的节点就是这个状态序列 |
| 认知动作 | Beat 的类型：立题 / 破除 / 给因 / 给法 / 建联 / 收束 |
| visual_operation | 认知操作对应的视觉操作，十种枚举（INTRODUCE…SUMMARIZE） |
| visual_delta | 该 Beat 在画面上造成的 add / modify / remove，认知变化到视觉揭示的桥 |
| visual_goal | 该 Beat 为什么必须画——不画观众会卡在哪 |
| reveal_order | Beat 内元素的先后顺序，等于分区编号顺序，等于旁白讲述顺序 |
| timing_role | Beat 在时间上的角色：锚点 / 承接 / 停留 |
| 词级锚 | 旁白里逐字出现的短语；卡上写 `anchors`，落到 `script.json` 即 `elements[].phrase` |
| 分区 / panel | 板图上一次被揭示的一块区域；`input/layout.json` 的 panels 与 `elements[]` 按序号一一对应 |
| 揭示窗口 | 一个分区在时间轴上被画出来的区间，由词级锚的边界决定 |
| 终图 | 最后一个 Beat 结束时画面停留的完整模型，也是全片认知模型的具象 |
| Reveal Constraint | P3 的形式化：`Visible ⊆ Required(n) + Deliberate Context` |
| 领先违规 | P3：视觉提前于认知，且未登记 `hook` |
| 落后违规 | P3 反方向：旁白已进新 Beat，画面仍在补上一 Beat 的元素超过一句 |
| hook | 卡上显式登记的悬念元素，P3 的唯一合法豁免 |
| 自造黑话 | P4 禁止的、只在本片成立的临时术语 |

## 6. 文档关系

```
principles（本文：为什么、判据从哪来）
   └→ knowledge-model（语义 IR：教什么 / 观众是谁 / 建什么模型 / 学到什么程度 / 不解释什么）
         └→ learner-model（转换器：约束求解 → Transition 规划 → Merge Test → Beat 数下界）
               └→ expression-plan（表达编译：expression_goal → 语言功能 + reveal 操作 + 通道分配 + 元素职责）
                     └→ cognitive-timeline（时序化：Scene 分组、reveal_order、Reveal Constraint）
                           └→ script-design（这一段具体怎么说：旁白、板图描述、分区与检查）
                                 └→ engine-design / kernel-design（确定性管线与渲染内核）
```

每条规则只在一处定义，其余文档引用不复述（`script-design.md` §1 只写判据编号）。
`quality-checklist.md` 只做可勾选清单，可复述条件但解释权在上述文档。
合成层实现物是 `assemble.py`（早期文档称 compose.py，以代码为准）。
主题与画风（`themes/`）独立于认知层，不参与任何认知决策。
